# CarSentinel 360 · 流媒体协议 v1

车机端（Android）与手机端（iOS）之间唯一的契约。两端各自实现，互不知晓对方语言。
本文档中的所有字段名、魔数、端口都是**冻结的**，改任何一项都要同时升版本号并改两端。

- 版本：`1`
- 传输：TCP + UDP，全部明文，不加密（局域网内使用；公网中继见文末扩展方案）
- 字节序：所有多字节整数均为 **大端（big-endian）**

---

## 1. 端口

| 端口 | 协议 | 方向 | 用途 |
| --- | --- | --- | --- |
| 45676 | UDP | 手机 → 广播 | 主动探测请求 |
| 45677 | UDP | 车机 → 广播 | 定时广播自己的存在 |
| 45678 | TCP | 手机 ↔ 车机 | 控制通道 + 视频通道（同一个端口，靠首字节区分） |

---

## 2. 设备发现（UDP）

### 2.1 车机端定时广播

车机端在服务启动期间，每 **1000 ms** 向 `255.255.255.255:45677` 发送一行 JSON（UTF-8，无换行）：

```json
{
  "t": "announce",
  "v": 1,
  "name": "CarSentinel-3F2A",
  "port": 45678,
  "cameras": [
    { "id": 0, "name": "前视", "pos": "front", "w": 1280, "h": 720 },
    { "id": 1, "name": "后视", "pos": "rear",  "w": 1280, "h": 720 }
  ],
  "caps": ["h264"]
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `t` | string | 固定 `"announce"` |
| `v` | int | 协议版本，当前 `1` |
| `name` | string | 车机显示名，长度 ≤ 32 |
| `port` | int | TCP 服务端口，即 45678 |
| `cameras` | array | 当前可用的摄像头列表，**可能只有 1~2 路**（见 §7） |
| `cameras[].id` | int | 摄像头编号，`0` 起，稳定不变 |
| `cameras[].name` | string | 人读的名字，如「前视」 |
| `cameras[].pos` | string | `front` / `rear` / `left` / `right` / `inner` / `unknown` |
| `cameras[].w` / `.h` | int | 该路输出分辨率 |
| `caps` | array | 编码能力，当前只有 `"h264"` |

### 2.2 手机端主动探测

手机端向 `255.255.255.255:45676` 发送 ASCII 串 `DISCOVER\n`。
车机端收到后**立即**回一条 §2.1 的 announce（单播回来源地址），不必等下一个 1 秒周期。

> 手机端应同时做两件事：被动收 45677 的广播（1 秒一次），
> 以及在进入「附近设备」页时主动发一次 DISCOVER。两者内容一致。

## 3. TCP 连接的第一步：首字节分流

手机端每开一条 TCP 连到 `45678`，**第一行**决定这条连接是什么：

| 首字节 | 会话类型 | 第一行内容 |
| --- | --- | --- |
| `{` | 控制会话 | 一个完整 JSON 对象，见 §4 |
| `S` | 视频会话 | `SUBSCRIBE <cameraId>\n`，见 §5 |

车机端读到第一个字节后即确定类型，后续不再改判。

---

## 4. 控制通道（JSON Lines）

一行一个 JSON 对象，`\n` 分隔，UTF-8。单行上限 **64 KB**。

### 4.1 手机 → 车机

| 消息 | 字段 | 车机响应 |
| --- | --- | --- |
| `{"t":"hello","role":"phone","v":1}` | — | `{"t":"welcome",...}` |
| `{"t":"list"}` | — | `{"t":"cameras","cameras":[...]}` |
| `{"t":"subscribe","camera":0}` | `camera` int | `{"t":"subscribed","camera":0}` 或 `{"t":"error","code":404,"msg":"no such camera"}` |
| `{"t":"unsubscribe","camera":0}` | — | `{"t":"unsubscribed","camera":0}` |
| `{"t":"keyframe","camera":0}` | — | `{"t":"ok"}`（请求立刻编一个 IDR） |
| `{"t":"stats"}` | — | `{"t":"stats",...}` |
| `{"t":"ping","id":<int>}` | — | `{"t":"pong","id":<同一个int>"}` |
| `{"t":"bye"}` | — | 车机关闭这条控制连接 |

> **实现说明**：车机端在 TCP 一接受连接就**主动先发一条 `welcome`**（不等 `hello`）。
> 这是允许的 —— 手机端把收到的第一条当作 welcome 解析，之后再到的 welcome 直接忽略。
> 好处是手机端不用先发 hello 就能拿到摄像头列表，连接建立到看见列表少一个往返。

### 4.2 车机 → 手机（主动推送）

| 消息 | 说明 |
| --- | --- |
| `{"t":"welcome","v":1,"name":"...","cameras":[...]}` | hello 的响应，附带当前摄像头列表 |
| `{"t":"cameras","cameras":[...]}` | list 的响应；摄像头集合变化时也主动推 |
| `{"t":"camera_state","camera":0,"active":true,"fps":30,"bitrateKbps":3500}` | 某路的实时状态，变化时推 |
| `{"t":"subscribed"/"unsubscribed",...}` | 订阅结果 |
| `{"t":"error","code":<int>,"msg":"..."}` | 错误；`code` 用 HTTP 语义（400 参数错 / 404 无此摄像头 / 409 已在订阅 / 500 内部错） |
| `{"t":"stats","cpu":0.42,"netKbps":9800,"uptimeSec":123}` | 车机整体状态 |
| `{"t":"log","level":"info","msg":"..."}` | 运维日志，手机端可显示在诊断页 |

### 4.3 保活

- 手机端每 **5 s** 发一个 `ping`。
- 车机端 **15 s** 没收到任何消息就断开这条控制连接。
- 视频会话独立保活：靠帧本身，见 §5.3。

## 5. 视频通道（二进制帧）

### 5.1 握手

手机端新建 TCP 连到 `45678`，第一行发送：

```
SUBSCRIBE <cameraId>\n
```

`<cameraId>` 是十进制整数。车机端回复一行 ASCII：

- `OK <w> <h> <fps> <codec>\n`，例如 `OK 1280 720 30 h264\n` —— 之后立即开始吐帧
- `ERR <code> <msg>\n`，例如 `ERR 404 no such camera\n` —— 然后关闭连接

### 5.2 帧格式

固定 **24 字节帧头** + 负载：

```
偏移   长度   字段          说明
0      4      magic         0x43 0x53 0x36 0x30，即 ASCII "CS60"
4      1      version       1
5      1      flags         bit0 = 关键帧(IDR)，其余位保留为 0
6      2      reserved      0
8      4      cameraId      uint32 大端
12     8      ptsUs         uint64 大端，微秒，单调递增即可，不要求与墙钟对齐
20     4      payloadLen    uint32 大端，帧头之后的负载字节数
24     ...    payload       H.264 Annex-B 字节流
```

### 5.3 负载：Annex-B H.264

- `payload` 是一串 `00 00 00 01` 起始码分隔的 NAL 单元。
- **每个 IDR 前面必须重带 SPS(7) 和 PPS(8)**。这条是硬要求：
  手机端可能在任意时刻加入，收到 IDR 时必须能立刻建解码器。
- 一帧可以含多个 NAL（例如 SPS + PPS + IDR + SEI），用起始码串起来即可。
- 不要求时间戳连续，不要求等距。

### 5.4 为什么用 TCP 而不是 UDP/RTP

局域网内 TCP 的可靠性让「丢包＝花屏」变成「丢包＝卡一瞬」，而手机端没有重传逻辑，
实现量差一个数量级。带宽 4 路 720p30 ≈ 10 Mbps，家用 WiFi5 完全够。
真要做公网低延迟时，在 §8 的中继里换 UDP 是两端都不用改的。

## 6. 手机端状态机

```
[扫描] --UDP announce/DISCOVER--> [设备列表]
[设备列表] --用户点某台--> [连接中] --TCP hello--> [已连接]
[已连接] --SUBSCRIBE cam0--> [四宫格] --点某格--> [单路全屏]
[单路全屏] --返回--> [四宫格]
[四宫格] --断开--> [设备列表]
```

- 四宫格最多 4 格；`cameras` 少于 4 路时只显示实际路数，空位不占网格。
- 单路全屏时只保留 1 条视频连接，退出时恢复四宫格需要的连接。
- 任何一条视频连接断开 → 该格显示「信号中断」浮层，控制连接保留，**自动重连该路**。
  手机端最多重连 5 次、每次间隔 1.5 秒；耗尽后停在该格显示「重连 N 次仍失败」。
  握手被车机端以 `ERR` 明确拒绝时不重试（那是「没这路摄像头」，重试没意义）。
- 收到帧头魔数不对或 `payloadLen` 离谱时，**必须直接断开重连**，不能只跳过 24 字节了事 ——
  不把 payloadLen 个字节吃掉，后面每一帧都会跟着错位，整条流永久变成垃圾。

## 7. 摄像头路数：为什么是 N 路而不是写死 4

普通 Android 设备（手机/平板/普通车机）**通常只能同时打开 1~2 个物理摄像头**，
4 路同时采集依赖硬件支持。因此：

- 车机端启动时**枚举**当前能同时打开的摄像头，把实际结果放进 announce 的 `cameras`。
- 协议里摄像头是**列表**，不是 4 个固定槽位。手机端按列表渲染。
- 采集层（Camera2 / CameraX / USB UVC）与编码推流层**解耦**：
  换采集源不改协议、不改手机端。接 4 路 USB 摄像头时，只需替换采集层实现。

## 8. 公网中继（后续，两端协议不变）

「随时随地查看」需要一台常开中转。因为视频就是普通 TCP 流，中继可以是纯 TCP 代理：

```
手机端 ──TCP──> 中继服务器 ──TCP──> 车机端
                 （按 ticket 配对）
```

需要新增的只有：
1. 中继服务器上的 ticket 颁发与配对（HTTP 接口）。
2. 车机端主动向中继注册（outbound 连接，车机在 NAT 后也能通）。
3. 手机端把「直连 IP」换成「中继地址 + ticket」。

视频帧格式、控制消息、手机端 UI **一行都不用改**。设计中继时优先保证
TCP 代理足够薄，不要在这层做转码。
